Conclusion: Sufficiently tight I/O caps + memory wipes are robust to all model sharding strategies. That is, verification of I/O caps + memory wipes can impose a large penalty on covert forward passes, regardless of how the prover tries to split up their model so that only part of it is inputted in each memory wipe cycle. This is essentially because any sharding forces the prover to pass at least one model activation per token through the bottlenecked I/O, which is slow. The tricky part is having strong enough I/O caps + memory wipes (perhaps: low Mbps and seconds-long memory wipes) to force the prover to do any model sharding and to make this sharding slow.
Argument
Let’s consider one sharding strategy: pipeline parallelism with 2 shards. If a covert I/O cap of, for example, 1 Mbps is imposed, then this strategy will be very slow.
In this strategy, the prover splits their model such that the early half of layers is one shard, and the later half of layers is the other shard. For each input token, the associated activation halfway through the model (potentially in compressed form) must be covertly outputted after the first shard is computed on, and covertly inputted before the second shard is computed on. Thus, a forward pass on one input token must take at least the time needed to pass one activation through covert I/O.
Thus, covert forward passes will be very slow, especially compared to training on large pods. For example, given a compressed activation size of 1 Kb per token and a cap of 1 Mbps, the resulting throughput will be at best 1,000 tok/s. For comparison, a super pod of 5e18 FLOP/s doing forward passes with 100% utilization at 1e12 FLOP/tok would have a throughput of 5 million tok/s, so the above would impose a 5,000x efficiency penalty on the forward passes.
A somewhat stronger argument can be applied to backward passes—they’d require passing activations and the activation error through I/O—but even without that, severely penalizing the forward passes is enough to throttle training. (But the argument here isn’t much stronger than with forward passes. The prover could input only one layers’ activations per shard and recompute the rest, for a ≤ 2x computation penalty, rather than needing to input every layers’ activations.)
The penalty increases linearly with the amount of sharding the prover does, since more shards require proportionately more activations per token to be passed through the bottlenecked I/O.
All model sharding strategies are at least as slow as the above. Intuitively, this is because we’ve only relied on the fact that the above sharding strategy requires passing a single activation per token through I/O, and any other sharding strategy requires at least that.
Any pipeline parallelism sharding with more than 2 shards would require strictly more I/O, further straining the I/O bottleneck, since then more than one activation would have to be passed through the I/O per input token.
Any tensor parallelism would also require more I/O than the above minimal pipeline parallelism, since tensor parallelism generally requires more communication than pipeline parallelism.
Expert parallelism works similarly to pipeline parallelism, also requiring at least one activation to pass through I/O per input token.
Any data parallelism is out of scope, since it’s not a model sharding strategy. If the prover doesn’t have enough I/O to infiltrate their full model, this isn’t a problem they can solve with data parallelism.

Caveats
There’s a moderate range of I/O caps and memory wipe speeds where the memory wipes impose meaningful, large penalties. 
If the I/O cap and memory wipe cycles are too large, then the prover won’t need to shard their model. If the I/O cap is very low, it would make training impractical even without memory wipes. 
The sweet spot where memory wipes are useful may be in the ballpark of low Mbps I/O caps and ~seconds-long memory wipes (enabling ~minutes-long memory wipe cycles while maintaining ~90-99% uptime). This seems to be higher than what’s needed to be confident in the I/O cap alone, yet tight enough to force sharding. (100 Mbps over a 100 second cycle = 10 Gb ≈ 1 GB.)
Secret storage could severely weaken the above argument/penalty. They would enable a prover to “save their work” by storing activations in the secret storage rather than needing to pass them through the bottlenecked I/O.
Applying I/O caps only at small pod scales could also severely weaken the above argument/penalty. 
For example, let’s compare three possible arrangements for 1,000 GPUs:
(A) 1 pod of 1,000 GPUs where the pod is subject to a 1 Mbps I/O bottleneck
(B) 100 pods of 10 GPUs where each pod is subject to a 1 Mbps I/O bottleneck
(C) 100 pods of 10 GPUs where each pod is subject to a 1 Mbps I/O bottleneck, and this whole collection of pods is further subject to an aggregate 1 Mbps I/O bottleneck
Options (A) and (C) both effectively impose a 1 Mbps I/O bottleneck on the 1,000 GPUs, but option (B) has a total of 100 Mbps I/O at its disposal.
The above argument applies to any forward pass, including decode, but then the penalty is smaller because the baseline throughput is lower.
The above is imprecise about whether I/O refers to the cap on input and output individually or in aggregate, but this just changes results by a factor of ~2, which is insignificant for these qualitative results.
